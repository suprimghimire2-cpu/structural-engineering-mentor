Executive summary
StructIQ is intended to become a professional-grade structural engineering knowledge and mentorship platform that
helps learners and engineers progress from first principles to analysis, design, advanced methods and professional
judgement. It should not be a glossary dressed as a website, a generic chatbot, or an unverified design calculator. Its
core differentiator should be the connection between physical behaviour, mathematical formulation, analysis, design
provisions, construction and engineering decisions.
The recommended strategy is to build in layers. Start with a dependable, sourced knowledge system and an excellent
structural-engineering user experience. Add interactive, independently verified educational mechanics tools. Then add
carefully scoped code-aware workflows and import/interpretation support. Advanced analysis, automated design and
AI-assisted engineering should come later, behind explicit validation, auditability and professional review.
The existing prototype is described by the project brief as a Vite + React JavaScript application with src/main.jsx,
src/styles.css, src/data/knowledge.js, src/components/, Knowledge/, scripts/, index.html, package.json,
package-lock.json, and vite.config.js. The brief says Knowledge, Mentor and Explore experiences exist to some
degree, but it does not establish that each feature is complete or production-ready. A developer must audit the
repository before changing it.
The governing product principle
Help users reason about structures, not merely retrieve formulas. Every concept should explain what it is, why it
matters, how it behaves, what assumptions and equations apply, how to interpret results, what can fail, which rules are
code-specific, and how the topic connects to a real structural system.
Five design commitments
 1. Engineering integrity: sources, equations, assumptions, units, applicability and verification are visible.
 2. Conceptual coherence: knowledge is a graph of prerequisites and relationships, not a flat list of pages.
 3. Progressive capability: education first; verified calculations next; advanced professional workflows only after validation.
 4. Professional product design: technical, architectural, restrained, accessible, readable and responsive—not generic
 AI/SaaS styling.
5. Preserve and improve: audit and protect the existing prototype before refactoring; never sacrifice working knowledge
 data for visual polish.
1. Purpose and product definition
1.1 What StructIQ is
StructIQ is a structural engineering knowledge, learning and mentorship environment, with a planned path toward
interactive analysis and design support. It should connect:
 • Core mechanics and strength of materials
 • Structural elements and systems
 • Structural analysis and interpretation
 • Materials and design methods
 • Loads, combinations and hazards
 • Foundations and the structure–geotechnical interface
 • Seismic, wind and structural dynamics
 • Codes, standards and jurisdictional application
 • Drawings, detailing, constructability and quality assurance

1.2 Audience and jobs to be done
Students and early-career engineers: build concepts in a sequence; connect formulas to physical behaviour; practise
with worked examples; diagnose misunderstandings.
Graduate/Master's-track learners: deepen matrix analysis, stability, FEM, dynamics, earthquake engineering, research
methods and critical evaluation of numerical models.
Practising engineers: access concise references, assumptions, cross-linked topics, code references, modelling
considerations and verification checklists. Any professional use must be transparent about scope and must not imply an
unreviewed answer is safe for construction.
Educators/researchers (later): curate material, construct learning paths, use case studies and compare conceptual
approaches across standards.
1.3 What StructIQ is not at first
It is not initially a replacement for an engineer of record, commercial structural analysis software, current licensed
codes, geotechnical investigation, peer review, site-specific judgement or regulatory approval. It should not claim to
generate construction-ready designs unless the complete technical, validation, legal and professional governance
framework exists.

3.1 Homepage narrative
The homepage should show, within seconds, that StructIQ is about real structural engineering. Recommended
sequence:
 1. Restrained navigation and clear product identity.
 2. Engineering-led opening composition: a meaningful frame, force/load-path drawing or structural section, not a generic
 stock building photo or oversized empty marketing hero.
3. Concise value statement: “Understand how structures work.”
 4. Clear actions into Knowledge and Mentor.
 5. A visual explanation of how knowledge connects: fundamentals → mechanics → analysis → member behaviour →
 design → systems → practice.
6. Structural element explorer connected to real concept IDs.
 7. A load-path/behaviour illustration that distinguishes gravity and lateral load transfer.
 8. Learning and practice preview.
 9. Global principles and code-specific layers explained without implying every code is already supported.
 10. Trust/reference section explaining source policy, review state and limitations.
 
3.2 Visual design system
Visual language: technical editorial design, engineering documentation, architectural drawing and carefully composed
software UI. Use technical grids, member labels, dimensions, section references, line-weight hierarchy and restrained
diagrams only where they clarify meaning.
Palette direction: graphite/charcoal, warm off-white, concrete grey, muted steel and a restrained olive/green accent.
Use status colour semantically: error, warning, informational and verified; do not decorate every element.
Typography: readable sans-serif for UI/body; restrained display face for main statements; monospaced technical labels
for dimensions, identifiers and metadata. Keep body text highly readable and information density deliberate.
Avoid: excessive rounded cards, gradients, glassmorphism, floating glows, random icons, unsubstantiated statistics,
decorative pseudo-technical labels, animation without meaning and stock engineering imagery that does not connect to
content.
Accessibility: target WCAG 2.2 AA as a design objective; use semantic HTML, keyboard operation, visible focus,
adequate contrast, accessible form labels, reduced-motion support, responsive text and diagrams with text alternatives.
W3C identifies WCAG 2.2 as the current recommendation and notes its relationship to ISO/IEC 40500. [R1]

4.1 Recommended concept record
Each concept should eventually support:
 • Stable ID and canonical title
 • Aliases, search keywords and discipline/category
 • Intended level and prerequisite concept IDs
 • Short summary and learning objectives
 • Physical intuition / behaviour
 • Definition and scope
 • Diagram or visualization specification
 • Assumptions and limitations
 • Variables, symbols and units
 • Equations with definitions, domains of validity and reference
 • Worked examples with unit-consistent steps
 • Interpretation and engineering implications
 • Failure modes and common misconceptions
 • Practice questions and solutions
 • Related concept IDs and relationship types
 • Code applicability where appropriate, kept separate from universal mechanics
 • References with publisher, title, edition/date, URL/DOI, access date and support statement
 • Review status, reviewer, last verified date and change history
 
4.2 Relationship graph
Represent relationships explicitly: prerequisite, applies-to, explains, used-in, design-check-for, failure-mode-of,
governed-by, illustrated-by and contrasts-with. This enables “learn next”, related concepts, learning paths and search
relevance without hard-coding these behaviours into UI components.
4.3 Knowledge quality states
Recommended labels:
 • Draft — incomplete, internal authoring.
 • Reviewed for learning — explanations and examples checked.
 • Calculation verified — computational result tested against trusted benchmarks and/or independent calculation.
 • Code reviewed — standard name, edition, jurisdiction and clause references checked.
 • Needs recheck — source changed, edition superseded or issue reported.
 A label must state exactly what was reviewed. “Verified” alone is too vague.

6. Codes and standards strategy: global, modular,
jurisdiction-aware
The platform should separate universal mechanics from local code rules. A code module needs metadata and change
control, not copied snippets of uncertain provenance.
6.1 Initial code-family map
 • Nepal: the Department of Urban Development and Building Construction official page currently lists, among others,
 NBC 105:2025 seismic design, NBC 104 wind load, NBC 103 occupancy load, NBC 110 plain and reinforced concrete,
NBC 111 steel, and multiple other NBC documents. Confirm exact adopted edition and legal applicability for each
deployment/jurisdiction. [R2]
• United States: ASCE/SEI 7-22 is identified by ASCE as the current edition on its standards page for minimum design
 loads and associated criteria; AISC 360-22 is the steel specification listed on AISC's current-standard page; ACI
CODE-318-25 is the current ACI concrete code offering on ACI's official page. Confirm adoption, errata and local
amendments before using them in a workflow. [R3–R5]
• Europe: Eurocodes provide a harmonised family of structural design standards. The European Commission's page
 describes the second-generation Eurocodes timeline: final official language texts to National Standards Bodies by no
later than 30 March 2026, publication deadline 30 September 2027 and withdrawal deadline for first-generation parts
30 March 2028. Track national annexes and national implementation. [R6]
• Global reliability principles: ISO 2394:2015, General principles on reliability for structures, was reviewed and confirmed
 in 2026 as current on the ISO page when checked. It provides a risk/reliability-informed basis for design and
assessment. [R7]
• Australia/New Zealand, UK, India and other markets: include only after edition, adoption, national annex/amendment
 and legal status are verified from the appropriate official body. Do not infer currency solely from a secondary website.
6.2 Code record model
Each coded rule should include:
 • Country/jurisdiction and authority
 • Standard identifier and full title
 • Edition/year, amendments and errata date
 • Status (published, adopted, superseded, draft, under review)
 • Scope and exclusions

7. Calculators and interactive visualisations
7.1 Recommended first calculators
Begin with educational tools that can be independently checked and have clear assumptions:
 1. Unit conversion with dimensional checks.
 2. Section-property calculator for common idealised shapes.
 3. 2D equilibrium/support reaction tool for simple statically determinate cases.
 4. Simply supported beam with a small verified set of load cases; show reactions, SFD, BMD and deflection under
 declared assumptions.
5. Axial deformation and elastic stress examples.
 6. Euler buckling calculator, clearly limited to ideal elastic columns with defined end conditions and slenderness
 assumptions.
Later: trusses, frame stiffness method, influence lines, RC/steel section design, slab actions, foundation sizing and
dynamic response. Each requires separate validation and standard-specific handling as appropriate.
7.2 Calculator result contract
Every calculation must display:
 • Input values, units and validation messages
 • Sign convention and coordinate axis
 • Assumptions and boundary conditions
 • Governing equations and variable definitions
 • Intermediate steps, not only the final result
 • Results with units and sensible precision
 • Checks or balance residuals (e.g., equilibrium)
 • Scope limitations and known exclusions
 • Reference/verification method and version number
 • Exportable calculation record and reproducibility metadata

8.2 Safety and reliability behaviour
 • State uncertainty and missing inputs; do not fabricate code clauses or source citations.
 • Distinguish educational examples from project-specific professional design.
 • Ask for missing parameters in calculation workflows rather than silently assume them.
 • Never imply a concept-only rule is universally applicable.
 • For code-sensitive decisions, identify jurisdiction, edition and applicability.
 • For high-consequence design, require licensed professional review and independent verification.
 • Log the model/system version and source versions for calculation-related output.

9. Search and discovery
Start with reliable local search over title, aliases, summary, category, keywords and related IDs. Add ranked search over
equations/symbols, material/system types and synonyms. Later add semantic search, but preserve citation/source
provenance and avoid returning a language-model answer without traceable support.
Search result should show why it matches, the subject level, source/review state and links to prerequisites. Provide
spelling/symbol aliases such as “BMD,” “bending moment diagram,” “M diagram” only when those aliases are vetted.
10. Technical architecture recommendation
Keep the initial stack lean. Do not introduce a backend, router or state-management library without an actual need;
likewise, do not keep growing a monolithic main.jsx.
10.1 Suggested logical structure
 src/
  app/                 # app shell, routing and error handling
  pages/               # Home, Knowledge, Mentor, Learn, Analysis
  components/          # shared navigation, layout, buttons, diagrams
  features/
    knowledge/          # search, taxonomy, concept detail
    mentor/             # tutor UI, prompts and source display
    learning/           # paths, lessons, progress
    calculators/        # UI wrappers for validated calculation modules
    visualization/      # diagram rendering and interaction
    standards/          # code metadata, edition status and references
  data/
    concepts/           # curated concept records
    pathways/           # curriculum sequence
    sources/            # source registry and review metadata
  domain/              # units, types, validation rules and domain models
  calculations/        # pure calculation functions + tests
  services/            # storage, search, API/AI gateway when needed
  styles/              # tokens, typography, components, page styles
  tests/               # unit, integration and visual regression tests
This is a target structure, not a demand to move every file immediately. Refactor incrementally and keep
IDs/relationships stable.
10.2 Technology layers
 • Frontend: existing React/Vite is suitable for the prototype; use accessible semantic components and a consistent token
 system.
• Numerical kernels: start with deterministic pure functions in JavaScript/TypeScript for simple validated mechanics
 tools; consider Python with NumPy/SciPy for server-side numerical features later. NumPy's official documentation
describes its array, linear algebra and numerical foundations. [R8]
• Research-grade solver integration: OpenSees is a framework for simulation of structural/geotechnical systems and
 dynamic response, with public user/developer docs. Treat integration as a later specialist task, not a quick substitute
for a validated solver. [R9]
• Visualization: start with SVG/canvas for conceptual diagrams and simple plots; choose 3D/FE visualisation libraries
 only after representative data/interaction is defined.
• Persistence: local storage is adequate for early preferences; use a database and authenticated API once accounts,
 multi-device progress, saved models or collaboration are real requirements.

11. Quality assurance and validation
11.1 Software QA
 • Unit test calculation functions and unit conversion.
 • Integration test navigation, search, concept selection and mentor workflows.
 • Test route refresh/deep links on the chosen host.
 • Test responsive sizes, keyboard-only navigation, focus states and reduced motion.
 • Run production build in CI on every pull request.
 • Keep dependency updates reproducible via lockfile.
 • Use error boundaries and meaningful empty/error states.
 • Track performance budget for initial load, diagram rendering and large knowledge datasets.
 
11.2 Engineering verification
For each calculator:
 1. Specify exact scope and assumptions.
 2. Derive/document equations.
 3. Build test cases manually from textbook/official references or benchmark examples.
 4. Compare independent implementations where feasible.
 5. Test units, signs, limiting cases and equilibrium/energy residuals.
 6. Test invalid, extreme and missing inputs.
 7. Record expected numeric tolerance.
 8. Require engineering review before release.
 9. Version the code and tests.
 10. Re-run regression cases after every change.
 For FEM/advanced results, add mesh convergence, boundary-condition checks, equilibrium and model
sensitivity/verification tests. Do not call agreement with one software package proof of correctness by itself.
11.3 Security and privacy
OWASP ASVS 5.0.0 is a useful framework for specifying and testing web application security controls. [R10] Apply
proportionate controls for authentication, authorisation, session handling, input validation, dependency risk, secure
secrets, logs and backups before adding user/project data. Do not store personal project files without clear retention
and access rules.

15. Key risks and mitigations
 1. Scope explosion: use a phased roadmap, not all features at once.
 2. False engineering confidence: label assumptions, validation state and intended use.
 3. Outdated standards: maintain edition registry, access date, errata and review schedule.
 4. Unverified calculators: test against independent benchmarks and require technical review.
 5. Generic AI UI: base visuals on meaningful engineering diagrams and content architecture.
 6. Monolithic implementation: separate page composition, data, domain logic, tests and styles incrementally.
 7. Broken existing features: baseline tests, small commits, regression checks and rollbacks.
 8. Data licensing/copyright: maintain permissions and citation records.
 9. AI hallucination: ground mentor responses in reviewed content, cite sources, disclose gaps.
 10. Project files/privacy: establish retention and access controls before uploads/accounts.
 11. Low performance: lazy-load heavy diagrams, keep the initial bundle modest and measure.
 12. Code-comparison ambiguity: compare only same scope, limit state, units and edition contexts.

Revision 1  23 October 2026
Purpose of this addendum
This revision makes one product pillar explicit and central: StructIQ is not merely a structural-engineering knowledge
library. It should let a learner take the same engineering problem and study how different structural standards
approach analysis, design and detailing.
Core learning loop: Learn the engineering behaviour → analyse the structure → select a code →
follow that code's design procedure → understand the resulting detailing → switch codes →
compare what changed and why.

1. The New Core Product Pillar
The platform should provide a dedicated Code Learning &amp; Comparison system. A user should be able to
study a structural concept without being forced to memorize isolated clauses, then move naturally from mechanics
and analysis into code-specific design and detailing.
The code system should answer five questions for every topic:
1. What is the engineering problem?
2. What is physically happening?
3. How is the problem analysed?
4. How does each selected code prescribe the design/check?
5. How does that prescription affect the final detail?
This preserves the original StructIQ philosophy of teaching engineering reasoning rather than presenting formulas in
isolation. The supplied product brief already establishes the importance of code-aware design, structural behaviour,
calculations and detailing; this revision makes their connection an explicit product workflow. ■filecite■turn28file0■
2. Code-Centred Learning Architecture
Every major engineering topic should eventually have a reusable content structure rather than a one-off article. The
same content model can support beams, columns, slabs, foundations, walls, steel members, connections and other
systems.
Layer
What the learner sees
Purpose
1. Engineering principle
Mechanics, behaviour, assumptions
Build transferable understanding
2. Analysis

Connect behaviour to structural response
3. Code method

Learn the standard's approach
4. Worked example

Make the method concrete
5. Detailing

3. Example: One RC Beam, Multiple Codes
The flagship demonstration should be an ordinary reinforced-concrete beam because it naturally connects structural
behaviour, analysis, design and detailing.
Step A — Define the problem
Span, support condition, section geometry, concrete properties, reinforcement properties, loads and design situation.
Step B — Understand behaviour
Show load → shear → moment → curvature → deflection. This follows the relationship-based teaching approach
already defined for StructIQ. ■filecite■turn28file2■
Step C — Analyse
Determine reactions and design actions. Visualise shear force, bending moment and relevant serviceability response.
Step D — Select a standard
Example: ACI 318. Present the applicable method, assumptions, equations, checks and references. Then repeat for
IS 456, Eurocode 2 or another supported standard.

Step E — Detail
Show how the selected design result becomes an actual reinforcement arrangement: bars, spacing, cover,
anchorage/development, laps where applicable, transverse reinforcement and constructability considerations.
Step F — Compare
Switch standards without changing the underlying structural problem. The comparison view should expose the
reason for differences, not merely display different numbers.
Important: code values, equations, clauses and limits must be tied to an identified standard edition and verified
source. The existing brief explicitly requires this discipline. ■filecite■turn28file5■

4. The Comparison Engine
Code comparison should be a first-class product capability, not a table bolted onto an article.
A comparison session should allow the learner to choose a structural topic, element, material and standards. StructIQ
then presents the same engineering problem through multiple code lenses.
Comparison dimension
Example
Scope / applicability
Which structural situation and material does the provision cover?
Design philosophy
How resistance, reliability and limit states are treated
Loads & combinations
How actions are factored/combined for the selected design situation
Analysis assumptions
Idealisation, redistribution, second-order effects, effective properties
Strength design
Flexure, shear, axial, torsion, stability or connection resistance
Serviceability
Deflection, cracking, drift, vibration or other limits
Detailing
Minimum reinforcement, spacing, anchorage, joints, confinement, connections
Terminology
Different names or definitions for equivalent concepts
Result interpretation
Why the outputs differ and what that means physically
The UI should visually distinguish three things: universal engineering principles, code-specific requirements,
and interpretation / commentary. This follows the original brief's requirement to distinguish universal principles,
code requirements, assumptions and standard differences. ■filecite■turn28file2■
5. Detailing as the Final Learning Step
A major differentiator should be the transition from calculation to a real structural detail. The platform should teach
that a calculated reinforcement quantity or member size is not the end of design.
For reinforced concrete, the learning sequence can become:
Analysis → design action → resistance calculation → required reinforcement → minimum/maximum limits →
shear → serviceability → anchorage/development → laps/splices → spacing → cover → confinement → final
detail.
For steel, the analogous sequence can become:
Analysis → member actions → section selection → strength checks → stability/buckling → serviceability →
connection design → detailing → constructability.
This directly extends the original product brief, which identifies structural detailing, anchorage, development length,
lap splices, beam-column joints, steel connections and constructability as important future domains.

10. What Makes This Feature Defensible
A large number of websites can provide formulas, PDFs or code excerpts. StructIQ becomes more differentiated
when it connects them into a coherent learning system:
Mechanics → Analysis → Code → Design → Detailing → Comparison → Engineering judgement.
The comparison layer should therefore not be a simple “which code gives the bigger number?” tool. It should teach
why a difference exists, whether the compared provisions are genuinely equivalent, what assumptions changed, and
whether the comparison is valid for the same design situation.

 StructIQ is an interactive structural-engineering learning and reference platform where
users can learn structural behaviour, analyse engineering problems, study how different
standards prescribe design, compare those approaches, and understand how the resulting
calculations become real structural detailing.
This should become a core requirement in future development decisions. New features should strengthen at least
one link in the chain Learn → Analyse → Code → Design → Detail → Compare rather than simply adding another
isolated page or tool.
