# StructIQ Engineering Development Protocol

This protocol applies to all future engineering-development tasks in this repository.

## Phase 1 — Scope and theory

Before coding, define the structural problem, assumptions, degrees of freedom, boundary conditions, sign conventions and units. Derive the governing equations, identify limitations and specify independent benchmark cases.

## Phase 2 — Test-first design

Write deterministic numerical tests before completing an implementation. Include hand-derived benchmarks, independent closed-form checks, equilibrium, compatibility where relevant, dimensions, boundary conditions, invalid inputs, limiting cases, symmetry and superposition. Expected results must not be generated by the implementation under test.

## Phase 3 — Implementation

Keep calculation logic in deterministic pure functions where practical. Separate UI from calculations. Calculations must be testable without a browser.

## Phase 4 — Independent verification

Challenge results using independent engineering relationships. Verify external and internal equilibrium, reactions, displacement constraints, member-force consistency, units, signs, residuals and independent reference cases. A returned number is not evidence of correctness.

## Phase 5 — Adversarial testing

Test zero, negative, missing, duplicate and invalid values/references; zero-length members; missing restraints; singular and unstable systems; boundary loads; very small and large valid inputs; and floating-point tolerances. Fail safely and explain invalid models.

## Phase 6 — Integration

Check UI interactions, navigation, visualisation, accessibility, responsive behaviour, errors and existing routes/features.

## Phase 7 — Regression and build

Run `npm run engineering:check` (the canonical validation, full test and production-build command). After a correction, rerun the relevant tests and then the full command. Do not fix unrelated warnings.

## Phase 8 — Final self-review

Inspect the complete diff for formulas, units, assumptions, hardcoded answers, misleading diagrams, dead code, removed/weakened tests and missing errors. Never change expected results merely to pass. Do not suppress a failure without understanding it. Allow at most five focused correction cycles for one issue; report unresolved problems. A passing suite is not proof of engineering correctness.

If any required verification cannot be performed, state that limitation explicitly. Do not claim browser verification unless performed.
